## 1. What exists and runs today

| Component | What it does |
|---|---|
| `control/pipeline.py` | Orchestrates detect → track → log for a video source, frame by frame. |
| `control/synthetic_source.py` | Deterministic synthetic video source ("demo mode") — proves the pipeline runs with zero camera/GPU/network. |
| `control/state.py` | A small explicit state machine (IDLE/RUNNING/STOPPED/ERROR) gating pipeline execution. |
| `detector/motion_detector.py` | **Default** backend. OpenCV background-subtraction (MOG2) blob detector — flags motion, not drones specifically. Zero extra dependencies. |
| `detector/torchvision_detector.py` | Pretrained SSDLite MobileNetV3 (COCO), used as a proxy by keeping `airplane`/`bird`/`kite` classes. Real learned features, not a drone classifier. |
| `detector/ultralytics_detector.py` | Optional YOLO adapter. **AGPL-3.0** — opt-in only, never imported unless explicitly selected. |
| `detector/drone_detector.py` | Single-class "drone" SSDLite, loads weights from `detector/train.py`. **Has real fine-tuned weights as of this pass** (`models/dut_v1/`, gitignored) — see §2. |
| `detector/train.py` | YAML-configured fine-tuning script for the drone-specific detector. Deterministic seeding, gradient clipping, structured hard-negative handling. |
| `detector/datasets/` | Unified dataset schema + registry (4 named public datasets) + license-provenance tracking (`license_id`/`commercial_ok`) + a concrete DUT Anti-UAV converter. |
| `tracker/iou_tracker.py` | **Default** backend. Dependency-free greedy IoU tracker. No re-identification. |
| `tracker/bytetrack_adapter.py` | Optional Apache-2.0 ByteTrack/SORT family wrapper (Roboflow `trackers` package). |
| `eval/` | The **only** place accuracy numbers are produced: a frozen-eval-set harness computing AP@0.5, small-object recall, false-alarm rate, latency, track continuity. |
| `tools/preannotate.py` | Runs a detector over video/images, emits COCO-format pre-labels for human review — not a labeling tool itself. |
| `tools/render_detections.py` | Draws predictions vs. ground truth onto real images/video for visual inspection — read-only, inference + drawing only. |
| `telemetry/logger.py` | JSONL structured event logging per pipeline run. |
| `ui/app.py` | Streamlit operator console — live run view, preset/backend selection, event log, demo mode. |
| `scripts/run_pipeline.py` | CLI entry point: `python scripts/run_pipeline.py --source <file\|demo> --detector {motion,torchvision,ultralytics,drone} --tracker {iou,bytetrack}`. |
| `scripts/license_audit.py` | Fails the build if a copyleft (AGPL/GPL) package ends up in the core (non-extra) dependency list. |

Run it: `make install && make demo` (zero-dependency default path), or
`make run-ui` for the Streamlit console. `pip install torch torchvision`
unlocks `--detector torchvision`/`drone`.

## 2. What is PROVEN — with real numbers

Source: **`eval/REPORT.md`**, generated by `eval/harness.py` against the
real, frozen DUT Anti-UAV detection-subset test split (2200 real images,
official split from Zhao et al., IEEE TITS 2022, arXiv:2205.10851),
using `detector/drone_detector.py` loaded with weights fine-tuned by
`detector/train.py` for 2 epochs on the same dataset's real 5200-image
train split.

| Metric | Value | Source |
|---|---|---|
| AP@0.5 (single-class "drone") | **0.1914** | `eval/REPORT.md`, `eval/output/dut_anti_uav_metric_card.json` |
| Small-object recall (area < 32×32px) | **0.2300** (195/848) | same |
| Latency, mean | **~57-63 ms/frame** (CPU, no GPU in this environment) | same |
| Throughput | **~16-17 FPS** (CPU) | same |
| Published baseline range on this exact split | 0.400 (fastest, YOLOX-ResNet18) to 0.683 (best, Cascade-RCNN-ResNet50) mAP | Zhao et al., Table II, cited directly in `eval/REPORT.md` |

**Read on this result:** 0.1914 AP@0.5 is well below every published
baseline for this dataset — and this pass (2026-07-23) replaced "expected
and unsurprising for a 2-epoch run" (an inference from the loss curve)
with a direct measurement of *why*: sampling the model's own raw
prediction scores across 15 real test images found 2,299 of them **all
within [0.4277, 0.4531]** — a band 0.025 wide, entirely inside one bin of
a ten-bin histogram. The classification head is not discriminating
drone-vs-background by location at all; that, not NMS or the training
learning rate (both directly tested — see below), is why the model
produces dozens to ~150 near-identical, near-constant-confidence boxes
per frame, scattered across nearly every frame, instead of a small
number of localized, high-confidence detections. **This model is not
currently usable as-is; it is proof the pipeline works end-to-end, not a
working detector.**

Three real bugs/hypotheses were found, tested, and fixed or ruled out
while producing this result, not worked around or assumed away:
- The first fine-tuning attempt diverged to `NaN` weights (234/476
  tensors) at the training script's previous default learning rate.
  Diagnosed on real data, fixed with gradient clipping + a lower default
  learning rate, verified by re-training and checking the weights
  directly for `NaN`/`Inf` (`docs/DECISIONS.md` entry #14).
- The evaluation harness previously reported false-alarm rate as `0.0`
  and track continuity as `1.0` when they were structurally
  unmeasurable on this eval set (see §3) — both looked like real, good
  results. Fixed to report an explicit not-measurable state instead
  (`docs/DECISIONS.md` entry #15).
- The "near-identical boxes" symptom above was tested against three
  concrete hypotheses (NMS missing/misconfigured, classification
  collapse, learning rate too high) rather than left as "probably just
  undertrained": NMS turned out to be present and correctly wired (just
  tuned loose — tightened, but zero-retrain AP@0.5 barely moved, 0.1895→
  0.1914); a real controlled learning-rate comparison (0.0005 vs. the
  current 0.001 — the task's assumption of a stale 0.005 default didn't
  match the file) made things *worse*, not better (AP@0.5 0.1606); the
  score-collapse hypothesis was the one confirmed by direct measurement.
  Full diagnosis in `docs/DECISIONS.md` entry #18.

## 3. What is NOT proven, or not measurable — and why

- **False-alarm rate: not measurable on the current eval set.** DUT
  Anti-UAV's test split has **zero hard-negative (no-drone) images** —
  every one of its 2200 images contains at least one labeled UAV. The
  false-alarm-rate metric is defined against hard-negative frames and
  has literally never been exercised against real data.
- **Track continuity: not measurable on the current eval set.** The
  detection subset is a bag of independent static images with no
  temporal relationship between them; the frozen eval set wraps each as
  its own single-frame "sequence" (the honest representation of that,
  not an approximation of a real sequence). An ID switch cannot occur
  with one frame per sequence, so this metric is undefined here, not
  perfect. DUT Anti-UAV's separate **tracking subset** (20 real
  multi-frame sequences) would make this measurable — **it has not been
  downloaded or ingested in this branch.**
- **IR/night imagery: not evaluated.** DUT Anti-UAV is visible-light
  only. No infrared/thermal data has been sourced, converted, or
  evaluated anywhere in this repo.
- **FPV-class / very-small / high-speed targets: not specifically
  evaluated.** The eval set's small-object recall (0.2300) is the
  closest existing signal, and it's weak — but no FPV-specific dataset
  or scenario has been tested.
- **Real-world (non-benchmark) footage: never evaluated.** Every real
  number above comes from a static-image research benchmark, not live
  camera footage, a real deployment environment, or footage resembling
  an actual operating scenario. `docs/coverage-matrix.md` (drone type ×
  lighting/weather × background × range/angle/speed × EO/IR) remains an
  empty template — zero rows logged.
- **`ui/app.py`'s live pipeline has never been run against the
  fine-tuned `drone` backend on real footage** — only against synthetic
  demo frames and, separately, the batch eval harness. Live-pipeline
  behavior (per-frame latency under Streamlit's rerun model, tracker
  interaction) with this specific model is unverified.

## 4. Dataset and license status

Full detail: **`docs/datasets.md`**. Summary:

| Dataset | Status | License (`license_id`) | `commercial_ok` |
|---|---|---|---|
| DUT Anti-UAV (detection subset) | **Downloaded, converted, in active use** | `UNVERIFIED` | `unknown` |
| Anti-UAV | Registry placeholder only, no data | `UNVERIFIED` | `unknown` |
| Drone-vs-Bird | Registry placeholder only, no data | `UNVERIFIED` | `unknown` |
| VisioDECT | Registry placeholder only, no data | `UNVERIFIED` | `unknown` |

**Flag for commercial use / acquisition due diligence:** DUT Anti-UAV's
own GitHub repository (`wangdongdut/DUT-Anti-UAV`) carries a real,
verified Apache-2.0 `LICENSE` file — but that repository contains only a
README and one example image. The actual dataset (images + annotations
this model was trained and evaluated on) is hosted externally on Google
Drive / Baidu Pan, with **no license statement found attached to the
dataset content itself**. Whether the Apache-2.0 grant is intended to
cover the dataset is not confirmed. Until a maintainer supplies the
authoritative text (the paper's data-availability statement, direct
author correspondence, or an explicit statement on the download page),
this dataset's `commercial_ok` stays `unknown` — and
`detector/train.py --commercial-only` (added this pass specifically for
this purpose) will refuse to train on it. **Practical effect: today's
research/development use is consistent with the dataset's evident
academic purpose, but no model trained on it should be sold, licensed,
or shipped commercially until this is resolved.**

Core runtime dependencies are all permissive (MIT/BSD-3-Clause/
Apache-2.0 — see `docs/licenses.md`); `scripts/license_audit.py` enforces
that no copyleft package can enter the core install path. The only
copyleft dependency in the repo (`ultralytics`, AGPL-3.0) is an opt-in
extra, never installed or imported by default.

## 6. What would move this furthest — three next steps, ordered

**1. Train longer, on the same data, before anything else.**
The single clearest signal in this document is that the current model
is undertrained, not fundamentally broken: 2 epochs, a stable
(non-diverging) loss curve that was still decreasing when training
stopped, and a visual failure mode (uniform low-confidence flooding)
that's textbook "hasn't converged yet" rather than a data or
architecture problem. This is the cheapest, fastest, lowest-risk lever
available — no new data, no new licensing question, no new code — and it
produces a second, directly comparable data point (same eval set, same
metric) to know whether this architecture/dataset combination can
actually approach the paper's published baselines (0.40-0.68 AP) or
plateaus well short of them. Do this before investing in anything below.

**2. Resolve DUT Anti-UAV's commercial license status.**
This is a business/legal task, not an engineering one, and it blocks
every downstream commercial path regardless of how good the model gets.
`docs/datasets.md` documents exactly what's confirmed (a real Apache-2.0
repo license) and what isn't (whether it covers the dataset itself) —
the concrete next action is contacting the dataset's authors or finding
an explicit data-usage statement, not more engineering work. Doing this
early avoids building further commercial-facing work on top of an
asset with an open legal question.

**3. Acquire a dataset with real hard negatives and/or ingest DUT's
tracking subset.**
Two of five metric-card fields (false-alarm rate, track continuity) have
never been measured at all — not "measured poorly," genuinely never
exercised against real data, because no real hard-negative frames or
real multi-frame sequences have been ingested yet. False-alarm rate in
particular matters enormously for any real deployment (an anti-UAV
system that cries wolf constantly is not deployable regardless of its
AP@0.5); DUT's own tracking subset (20 real sequences, same source,
same license question as §4) is the cheapest way to make track
continuity measurable, and Drone-vs-Bird (already a registry
placeholder — see `docs/datasets.md`) is the most direct source of
structured hard negatives this repo's training code already knows how to
consume.
